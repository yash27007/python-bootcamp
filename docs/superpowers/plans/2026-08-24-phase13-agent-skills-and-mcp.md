### Task 1: Agent Skills — Progressive Disclosure

**Files:** Create `15-agent-skills-and-mcp/01-agent-skills/` (README.md, notes.md, notebook)

**Content:** Problem = an agent with access to hundreds of possible capabilities (specialized workflows, domain instructions, tool-usage patterns) can't have all of them loaded into its context at once — context windows are finite and most of those capabilities are irrelevant to any single task. Why-simpler-fails = "just put everything in the system prompt" doesn't scale: cite a concrete measured cost (token/character count) of loading N skills' full instructions vs. just their one-line descriptions, and note that even where it technically fits, irrelevant instructions dilute the agent's attention on what actually matters for the current task. Conceptual foundation (documented substitution) = formalize **progressive disclosure**: a skill is a self-contained package (a short name + one-line description always visible, and a full instructions body loaded ONLY when the skill is actually selected for use) — this is precisely the two-tier structure this very repo's own `.claude/plugins/.../skills/*/SKILL.md` files use in practice; cite that as a real, live example you can point to in your own environment (read a couple of real skill files from this repo's actual skills directory if accessible, to ground the description in something real rather than invented). Contrast with a "flat" model where every skill's full body is always loaded. From-scratch = implement a minimal `Skill` class (name, description, instructions-body, maybe a metadata frontmatter parser) and a `SkillRegistry` that holds N toy skills (write 4-5 small toy skill files with realistic short descriptions + bodies, your own invented toy examples, e.g. "csv-cleaning", "email-drafting", "code-review-checklist"); implement a deterministic (non-LLM) skill-SELECTION heuristic — e.g. keyword overlap between a toy task description and each skill's description — that picks the most relevant skill for a few toy task prompts, actually run it and show it picking correctly on a few real examples. Practical/Experiment = actually measure and compare total-context-characters-loaded under progressive disclosure (only descriptions + the one selected skill's body) vs. the flat "load everything" baseline, across a growing number of registered skills (e.g. 5, 20, 50 skills) — real numbers, real measured savings, plotted or tabulated. Failure modes = a selection heuristic picking the WRONG skill because of superficial keyword overlap (demonstrate a concrete real example where your heuristic gets it wrong), skill description conflicts/overlap making selection ambiguous. Real-world usage = cite Anthropic's Agent Skills feature and this repo's own use of Claude Code skills (superpowers plugin) as the direct real-world instance. Mental model, Questions.

### Task 2: Model Context Protocol (MCP)

**Files:** Create `15-agent-skills-and-mcp/02-model-context-protocol/` (README.md, notes.md, notebook)

**Content:** Problem = Task 1's skills package *instructions* for an agent to follow, but an agent also needs a standardized way to actually DO things — call external tools, read external resources — without every agent/tool pair inventing its own bespoke integration (cite `14-multi-agent-systems/01-communication-protocols`'s FIPA-ACL-performative point as the same underlying need — a standard message shape — applied to tool use specifically). Why-simpler-fails = one-off custom integrations per agent-tool pair don't compose: N agents x M tools needing bespoke glue code each is an N×M integration problem; a standard protocol makes it N+M. Conceptual foundation = formalize MCP's real architecture precisely: a client-server model over JSON-RPC 2.0 (real wire format: `{"jsonrpc":"2.0","id":..,"method":..,"params":..}` requests, `{"jsonrpc":"2.0","id":..,"result":..}` or `{"error":..}` responses), the three core primitives — **tools** (invocable functions with a JSON-schema-declared interface), **resources** (readable data the server exposes), **prompts** (reusable prompt templates the server provides) — and the discovery flow (`list_tools`/`list_resources` before any `call_tool`/`read_resource`). From-scratch = implement a minimal MCP-shaped server (registers 2-3 toy tools with real JSON-schema parameter definitions, e.g. a `add(a, b)` calculator tool and a `word_count(text)` tool) and a minimal client that actually speaks real JSON-RPC 2.0 messages to it (prefer a real local subprocess over stdio if it proves reliable in this environment; otherwise fall back to in-process JSON-RPC-message-shaped calls and say so honestly) — actually run: client discovers the server's tools via a `list_tools` call, calls one with real arguments, gets a real result back, shows the raw JSON-RPC message transcript. Experiment = hypothesis that schema validation catches a malformed tool call before it reaches the tool function (e.g. wrong argument type) — actually implement a basic JSON-schema check and demonstrate it rejecting one bad call and accepting one good call, real output. Failure modes = a tool call with a missing/malformed required argument, a server exposing a tool whose description is ambiguous enough that tool-selection (by a real agent, hypothetically) would be error-prone, protocol version mismatch. Real-world usage = cite the real MCP spec (Anthropic's Model Context Protocol) and real MCP servers/clients (Claude Code's own MCP tool integration — this session's environment has deferred MCP tools listed in its own tool list, e.g. `mcp__claude_ai_Notion__*` — a real, live instance of exactly this protocol in the environment this work is happening in, cite it by name without calling it). ### Task 3: Putting It Together — A Toy Skills+MCP Agent Loop

**Files:** Create `15-agent-skills-and-mcp/03-skills-and-mcp-agent-loop/` (README.md, notes.md, notebook)

**Content:** Problem = Task 1 (skills) gives an agent instructions for HOW to approach a task; Task 2 (MCP) gives it a standard way to actually DO things — but neither alone is a working agent; something has to tie skill-selection to tool-invocation in a loop. Why-simpler-fails = doing skill selection and tool calling as two totally separate, uncoordinated systems means the agent has no way to let its selected skill inform which tools it should reach for (cite Tasks 1 and 2's separate registries explicitly). Conceptual foundation = formalize a minimal agent loop: given a task, (1) select a skill from Task 1's `SkillRegistry` (reuse it directly, don't reimplement), (2) using that skill's instructions as context for which tool(s) are relevant, discover available tools from Task 2's MCP-shaped server (reuse it directly), (3) invoke the appropriate tool with real arguments extracted deterministically from the task (non-LLM heuristic — e.g. simple parsing/regex on the toy task string, stated honestly as a stand-in for what an LLM would do), (4) return a result. Connect explicitly to `14-multi-agent-systems/02-orchestration-patterns`: this loop IS a (single-agent, sequential) orchestration pattern — decompose (skill selection) → delegate (tool call) → aggregate (return result) — name that connection directly. From-scratch = actually build and run this loop end-to-end on 2-3 toy tasks (e.g. "clean this CSV string" routing to the csv-cleaning skill + a matching tool, "count words in this text" routing to word-count), real output at each of the loop's 4 stages, captured in the notebook. Experiment = hypothesis that reusing Task 1's skill-selection heuristic to narrow which tools are even considered (vs. considering all registered tools every time) reduces wrong-tool-invocation errors as the number of registered tools grows — actually implement both variants (skill-narrowed vs. consider-everything) and measure/compare on a batch of toy tasks with a growing tool registry (e.g. 5, 15, 30 tools). Failure modes = a skill selecting a tool that doesn't actually exist in the current MCP server's registry (a real integration-mismatch bug, demonstrate it and how you'd detect it), the deterministic argument-extraction heuristic failing on a task phrased differently than expected (show a concrete failure). Real-world usage = this loop, scaled up with a real LLM instead of a keyword heuristic and real external MCP servers instead of toy in-process ones, is architecturally what production agent frameworks (Claude Code itself, Claude's own Agent SDK, and general "tool-using LLM agent" systems) actually do — say so plainly, this is the curriculum's own capstone connection.
